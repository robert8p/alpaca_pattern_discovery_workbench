# Alpaca Pattern Discovery Workbench 1.1.0

A button-driven companion to the **Alpaca Rapid Discovery Loader**. The loader populates `rd_` market-data tables; this workbench reads those tables and writes only to independent `ra_` analysis tables.

## Purpose

The workbench turns accumulated Alpaca bars into a controlled research workflow:

1. Check database quality and coverage.
2. Freeze a liquidity-ranked equity universe.
3. Generate versioned intraday predictors and future outcome labels.
4. Scan interpretable rule families across discovery and validation periods.
5. Review exact candidate definitions and evidence.
6. Run a separately triggered sealed-period evaluation.

## 1.1.0 audited release

Version 1.1.0 replaces the v1.0.7 discovery engine and withdraws all candidate results generated by earlier rule definitions.

The release adds:

- Psycopg-compatible validation for every generated SQL query and parameter tuple.
- Machine-safe category codes; human labels containing percent signs never enter parameterised SQL.
- PostgreSQL `EXPLAIN` preflight before discovery or sealed-test jobs can be queued.
- Consistent bucket boundaries between discovery, validation and sealed evaluation.
- Identical entry sampling and cost treatment in all three periods.
- Explicit null handling in every categorical rule dimension.
- Regular-session and forward-horizon compatibility checks.
- Versioned candidate methodology: sampling mode, stride, anchor and rule-definition version.
- Dependency-safe deletion in the dashboard.
- A PostgreSQL-backed synthetic end-to-end test and mandatory GitHub Actions release gate.

Existing completed **feature sets remain usable**. Existing discovery results are treated as legacy and must be rerun.

## Safety boundary

Application code may select from:

```text
rd_bars
rd_assets
rd_inventory
rd_jobs
```

It writes only to `ra_` tables. The automated release audit scans the repository for prohibited writes against `rd_` tables.

For database-enforced protection, use a dedicated PostgreSQL role with read-only access to `rd_` and write access to `ra_`.

## Intraday predictors

The feature layer includes:

- Historical 1-, 5-, 15-, 30- and 60-minute returns
- Return from the session open
- Cumulative high, low and VWAP
- Distance from cumulative VWAP
- Position within the cumulative session range
- Prior-20-bar relative volume and trade count
- Rolling volatility and range
- Same-minute volume baselines using only prior dates
- Previous regular close and opening gap
- Previous-day return, range, volume and volatility
- Time, weekday and liquidity tier

Fields beginning with `fwd_` are future outcome labels and are never used as rule predictors.

## Discovery families

- Time of day and weekday
- Oversold / prior-decline conditions
- Prior-rise / momentum continuation
- VWAP deviation and range position
- Opening-gap behaviour
- Relative-volume shocks

Discovery defaults to **non-overlapping entries**: a 30-minute holding-period test evaluates entries every 30 minutes. Every-bar sampling remains available for diagnostics and is validated independently.

All displayed median return, win rate, t-statistic, profit factor, lower-tail return and worst return are net of the configured round-trip cost. Gross and net average returns are both retained.

## Important interpretation limits

- Results are conditional event returns, not a capital-constrained portfolio simulation.
- Broad buckets, holdouts and concentration controls reduce overfitting but do not eliminate multiple-testing risk.
- Current-active asset metadata can introduce survivorship bias.
- Fund exclusion is heuristic; inspect the frozen universe.
- A month of data is suitable for pipeline validation and hypothesis generation, not final trading confidence.
- A candidate should not be promoted on win rate alone; require positive net expectancy, adequate samples, low concentration and validation stability.

## Runtime and connection

- Python 3.12.7
- FastAPI web service
- Separate background worker
- PostgreSQL/Supabase
- Supabase **Primary Session pooler on port 5432**

Port 6543 and read-replica endpoints are rejected.
